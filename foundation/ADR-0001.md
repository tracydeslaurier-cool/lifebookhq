# ADR-0001 — Replace AuthorityBasisRecord with basis_claim_id → Claim
**Status:** Accepted  
**Date:** 2026-07-23  
**Deciders:** Discovery Partner + Claude (architecture session)  
**Supersedes:** None  
**Superseded by:** None

---

## Context

`GOVERNANCE_MODELS.md §2` defined a structured authority basis model — a set of fields (`authority_basis_type`, `authority_basis_record_id`, `source_id`, `jurisdiction_id`, `document_reference`, `basis_notes`) intended to replace free-text `legal_basis` on every attribute record and authority assignment.

`authority_basis_record_id` referenced a table called `AuthorityBasisRecord`. That table was never designed. It was listed as a migration blocker (G1) in PRE_MIGRATION_CLOSURE.md v1.2 and as a design gap in ARCHITECTURE_FREEZE_V1.md v1.1.

The question: is `AuthorityBasisRecord` the right design, or does a better pattern already exist in the architecture?

---

## Decision

**Eliminate `AuthorityBasisRecord`. Replace `authority_basis_record_id` with `basis_claim_id → Claim` (nullable FK) on `AuthorityAssignment` and on any other attribute record that carries the structured authority basis.**

---

## Rationale

The documentary basis for an authority assignment — a court order, a power of attorney, an SDM agreement, a will — is a sourced, evidenced, temporal, and potentially disputed fact about a person. This is exactly the kind of fact that **P2 — Claims own facts** places in the Claim layer.

`AuthorityBasisRecord` would have been a new table holding source-provenance metadata about a legal instrument. The Claim table already does this:

| What AuthorityBasisRecord would have held | How Claim provides it |
|---|---|
| Which document establishes the authority | `Claim.source_id → Source` |
| What kind of authority it establishes | `Claim.predicate_id → ClaimPredicate` (e.g., `is_guardian_of`, `has_power_of_attorney_over`) |
| Who holds authority over whom | `Claim.subject_entity_id` (the governed person), `Claim.object_entity_id` (the authority holder) |
| When the authority is in effect | `Claim.effective_from` / `Claim.effective_until` (or via predicate semantics) |
| Whether the authority is disputed | `Claim.dispute_status` → ContestRecord |
| How well-evidenced it is | `Claim.evidence_status` |
| Access classification | `Claim.access_classification` |
| External document reference | `Source.external_reference` or `Source.metadata` |

Adding a seventh parallel table to hold these fields would have replicated the Claim layer's responsibility. The Claim layer is already the system of record for sourced, temporal, provenance-tracked facts. `basis_claim_id → Claim` routes through that system rather than duplicating it.

---

## Consequences

### Changes to GOVERNANCE_MODELS.md §2 and §3.1

**Removed from the structured authority basis block (§2):**
- `authority_basis_record_id` → AuthorityBasisRecord
- `source_id` → Source (now carried on the referenced Claim)
- `jurisdiction_id` (from §2 only — it remains as a standalone field on AuthorityAssignment §3.1 for direct query access)
- `document_reference` String (now in Source referenced by the Claim)

**Retained:**
- `authority_basis_type` — kept as a quick discriminator on AuthorityAssignment to support application logic without requiring a join to the Claim
- `basis_notes` — operational annotation distinct from the evidentiary content of the Claim; retained for steward-facing notes

**Added:**
- `basis_claim_id` → Claim (nullable FK) — the Claim carries full evidentiary detail

### Changes to ClaimPredicate catalogue

The ClaimPredicate catalogue (v0.2, 74 predicates) must include predicates for the authority basis types that require representation as Claims. These are additive seed-data additions, not schema changes.

Required predicates (to be added to CLAIM_PREDICATE_CATALOGUE.md as Family additions — likely Family 2 Legal/Authority):
- `is_guardian_of` (parental_guardianship, court_appointed_guardianship)
- `holds_power_of_attorney_over` (power_of_attorney_general, power_of_attorney_personal, enduring_power_of_attorney)
- `is_executor_for` (testamentary_executor)
- `is_estate_administrator_for` (estate_administrator)
- `holds_cultural_authority_over` (cultural_authority)
- `is_supported_decision_maker_for` (supported_decision_making)
- `is_legal_representative_of` (legal_representative)

`self_assertion` and `policy_default` do not require a Claim (`basis_claim_id` is null for these).

### AuthorityAssignment migration dependency

`AuthorityAssignment` depends on `Claim` via `basis_claim_id`. `Claim` must therefore exist before `AuthorityAssignment` in the migration sequence. This is already consistent with the revised sequence in MIGRATION_SCOPE_MATRIX.md v1.1 (content tables — step 16 — precede AuthorityAssignment — step 15 in the original; this ordering must be corrected: AuthorityAssignment must come after Claim).

**Revised AuthorityAssignment migration position:** after ApprovalRecord and after Claim (and ClaimPredicate seed). This pushes it to step 16.5 in the MIGRATION_SCOPE_MATRIX.md sequence.

### PersonName.legal_basis

`PERSON_ATTRIBUTE_CATALOGUE.md` PersonName table retains a free-text `legal_basis` field. When PersonName is updated as part of the G2 (confidence normalization) pass, `legal_basis` should also be replaced with `basis_claim_id → Claim` and `authority_basis_type`, consistent with this decision. This is a G2 extension, not a new blocker.

### G1 blocker resolved

Blocker G1 (AuthorityBasisRecord not yet designed) is closed. `AuthorityAssignment` is now structurally complete. No design gap remains for that table.

---

## Alternatives considered

**Design AuthorityBasisRecord as a new table.** This would have been a fresh table with source-provenance fields, essentially duplicating the Claim layer for a specific domain. Rejected: violates P2 and adds surface area without adding capability.

**Use a JSONB blob on AuthorityAssignment.** This would have embedded document-reference metadata as unstructured JSON. Rejected: loses evidence tracking, dispute handling, and access classification that the Claim layer provides automatically.

**Keep free-text `legal_basis`.** Rejected: explicitly superseded in GOVERNANCE_MODELS.md §2; provides no machine-readable structure for governance logic.
