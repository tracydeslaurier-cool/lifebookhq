## Context

LifeBook stores governed assertions about living and deceased persons, including sensitive biographical, medical, legal, cultural, and identity information. The schema was designed across a multi-session architecture process. By the time the final pre-SQL specification was complete (VOCABULARY_RLS_MATRIX.md v3.0), the governance enforcement model had grown to:

- 53 RLS policies
- 22 triggers
- 9 helper functions (8 requiring SECURITY DEFINER)
- A three-layer separation between governance rules, enforcement strategy, and SQL implementation
- A hard architectural distinction between database invariant enforcement and application workflow

This ADR records why the enforcement architecture was built the way it was. It is the authoritative rationale document for implementation decisions that would otherwise appear arbitrary in migration SQL. Any future engineer reviewing the schema or proposing changes must read this document before modifying any RLS policy, trigger, or helper function.

---

## Decision

**Govern LifeBook data through a layered, fail-closed, database-enforced governance model in which:**

1. Row-Level Security is the primary actor-scoping mechanism for all content tables
2. Triggers enforce structural invariants that cannot be expressed as declarative constraints
3. SECURITY DEFINER helper functions isolate privileged reads required by RLS from the policies that invoke them
4. Application workflows are responsible for governance orchestration; the database is responsible for governance invariants
5. Historical records are immutable at the database layer — not by convention
6. AI and cultural governance are enforced as absolute exclusions, not advisory restrictions
7. Every access decision defaults to deny in the absence of an explicit permission

---

## Rationale

### 1. Why RLS, Triggers, and Helper Functions Are Required

**The access control problem in LifeBook is not uniform.** A Claim record is not simply owned by a user — it is scoped to a LifeBook, has a subject entity, has a review status, has an access classification, and may be culturally governed. The decision of whether the current actor may read a Claim is a function of at least five independent conditions. No application-layer access check can be made mandatory across all code paths, all service roles, and all future query contexts. The only reliable enforcement point is the database.

**RLS is the correct tool because it enforces access at the row level for every SQL operation regardless of which code path issues the query.** It does not rely on the application remembering to check. It does not fail when a new service role is added. It fails loudly when violated rather than silently permitting access.

**Triggers are required for invariants that cannot be expressed declaratively.** PostgreSQL CHECK constraints can validate individual field values at the time of a write. They cannot express temporal constraints (this field may only transition once), relational invariants (this status transition is only permitted when a ContestRecord exists for this row), or structural invariants that depend on parent row state (this rule may not be updated because the parent policy is active). These invariants are real, consequential, and non-negotiable. Triggers are the only mechanism that enforces them reliably.

**Helper functions are required because RLS policies on one table must read data from other tables, and those other tables also have RLS.** Without a function that bypasses RLS under a controlled security context, reading `lifebook_memberships` from within a `claims` RLS policy would either fail (denied by memberships RLS) or produce a recursive evaluation loop. The SECURITY DEFINER pattern resolves this by granting the function the privilege to read the required table directly, while restricting what the function may return to the calling policy. The alternative — disabling RLS on lookup tables — would compromise the entire access model.

### 2. Why Governance Rules Are Separated from Application Workflow

**The database enforces invariants. The application orchestrates workflows.** This distinction is architectural and must be preserved.

A governance workflow such as supersession of a DisplayPolicy involves five ordered steps: create successor, create rules, attach to governed record, supersede predecessor, activate successor. This is a workflow. The database is not aware of the intended sequence. It does not check whether step 3 preceded step 4. It does not care that the application intended a supersession rather than an unrelated status change.

What the database does enforce is the invariants that guarantee the result of any operation is structurally valid: an active DisplayPolicy record may not have its content-fields modified (trigger); a DisplayPolicyRule belonging to a non-draft policy may not be deleted (trigger); a DisplayPolicy with status = superseded may not be updated by any role (RLS + trigger). These invariants prevent incorrect outcomes regardless of what the application does. They do not prescribe the sequence.

**This separation matters for three reasons:**

First, business workflow logic placed inside database triggers creates a maintenance trap. Any change to the workflow — adding a new required step, modifying the order — requires a trigger migration. Trigger migrations are high-risk. Application-layer workflow changes are low-risk and do not touch the schema.

Second, trigger-enforced workflow logic cannot be tested independently of the database. Application workflow logic can be unit-tested against mocks. The only safe boundary is: triggers enforce what the data must always be; applications enforce what the process must do.

Third, governance rules are durable. The LifeBook governance model reflects real-world legal and ethical obligations. Immutability of historical records, the requirement that AI cannot self-promote, the absolute exclusion of culturally governed content from AI context — these are not implementation preferences. They are commitments to the people whose lives are stored in the system. They belong in the database, not in application logic that can be bypassed by a service role or a maintenance script.

### 3. Why Historical Records Are Immutable

**The biographical and governance information in LifeBook concerns real people, real relationships, and real legal instruments.** A person's birth record, their legal name, a family relationship, a steward's authority assignment — these are not draft documents. Once a record enters an active governance state, it becomes part of an auditable historical chain.

**Immutability serves three distinct purposes:**

**Auditability.** If a governed record can be modified in place, the system has no reliable history. When a dispute arises about what was asserted and when, the database cannot answer it. If a person's consent status changes, the system cannot reconstruct what information was released while the prior consent was in force. Immutability means every assertion is preserved with its provenance, its timestamp, and its evidence status.

**Protection from accidental or malicious overwrite.** A steward with database access, a poorly written migration, a service role with excess privileges — any of these can corrupt mutable records silently. An immutable schema converts a silent overwrite into an auditable supersession. The prior record remains. The new assertion is a new row with its own provenance.

**Compliance with the governance model's own rules.** The governance model specifies that Claims are superseded rather than overwritten. This is not an optional feature. The trigger `trg_claim_content_immutable` exists because the governance model requires it. If the trigger were removed, the governance model's promise — that every assertion is traceable — would no longer hold.

**Historical records are not made immutable for performance reasons or technical convenience.** They are immutable because the people whose lives are in the system are entitled to know that their records have not been modified.

### 4. Why AI and Cultural Governance Require Explicit Enforcement

#### AI governance

AI agents receive data through a Context Broker, operate on that data to generate candidate content, and return results that enter the governance layer at the lowest trust tier. This pipeline is correct. The problem is that it depends on the Context Broker behaving correctly in every future implementation.

**The database-layer AI restrictions are independent of the Context Broker.** Even if the Context Broker were compromised, misconfigured, or replaced by a new implementation that did not check AI restrictions, the following would still be true:
- Agent service role cannot INSERT into `events` (RLS #33)
- Agent service role cannot INSERT into `approval_records` (RLS #34)
- Agent service role cannot UPDATE `review_status = 'policy_approved'` on any AI-generated record (RLS #30, #32)
- Agent service role cannot SELECT any `access_classification = 'culturally_governed'` record (RLS #37–40)

These are database guarantees, not application promises. An AI agent that bypasses the Context Broker entirely — by connecting directly to the database under the agent service role — encounters the same restrictions. This is defense-in-depth for the most consequential boundary in the system.

**AI governance at the database layer also documents intent.** When a new engineer reads the RLS policies on `claims`, they see that AI promotion to `policy_approved` is denied. They do not need to understand the Context Broker architecture or read the governance documents to know that this is a hard constraint. The schema is self-documenting on this point.

#### Cultural governance

Cultural governance is treated differently from all other access classification levels. `access_classification = 'restricted'` is enforced by RLS but may be overridden by a steward with appropriate authority. `access_classification = 'culturally_governed'` is enforced by absolute exclusion from the AI context regardless of any DisplayPolicy or any steward override. This asymmetry is deliberate.

**The reason is that culturally governed content represents not just personal privacy but community sovereignty.** A cultural authority's jurisdiction over sacred, ceremonial, or community-specific information is not a preference. It is an obligation rooted in Indigenous data sovereignty principles and in the specific trust relationship that LifeBook is building with Indigenous communities. That obligation is not reducible to a configurable DisplayPolicy. It cannot be overridden by a steward decision. It cannot be permitted by an AI context manifest. It cannot be approved by a non-cultural-authority ApprovalRecord.

**The absolute AI exclusion (Invariant 7) is therefore not a technical restriction — it is a promise.** The promise is that LifeBook will never silently include culturally governed content in an AI context, regardless of what any policy or service role configuration says. Making this a database-layer invariant rather than an application-layer policy is the only way to make the promise trustworthy.

### 5. Why Fail-Closed Behaviour Is Mandatory

**Fail-closed means that the absence of an explicit permission is a denial.** This is the opposite of fail-open, where the absence of an explicit restriction is a permission.

**The LifeBook governance model requires fail-closed behaviour for the following reason:** the system stores information about living persons, deceased persons with active estates, persons with disputed authority situations, and culturally governed communities. In any of these cases, the consequence of accidentally permitting access is a harm — privacy violation, breach of cultural trust, compromise of a governance dispute. The consequence of accidentally denying access is an inconvenience — the steward or subject contacts support, the policy is corrected, access is restored.

These consequences are not symmetric. Fail-open optimises for convenience at the cost of safety. Fail-closed optimises for safety at the cost of occasional inconvenience. The architecture chooses safety.

**Concretely, fail-closed means:**

- If `display_policy_id IS NULL` on a governed record, the default decision for all public and export contexts is deny, not allow. The steward must attach a policy that explicitly permits the access.
- If a DisplayPolicy exists but has no rule for the requested display context, the decision is deny. A missing rule is not permission.
- If `fn_display_policy_allows` receives a NULL policy_id, an inactive policy, or a policy with no matching context rule, it returns FALSE.
- If `fn_lb_membership_role` cannot find a membership record for the current user, it returns 'none', which denies all access.
- If the cultural authority check cannot find an active AuthorityAssignment, the decision is deny.

**Fail-closed behaviour requires explicit design.** Left to defaults, PostgreSQL denies all access when RLS is enabled with no policies — which is correct. The risk is in the policies themselves: a policy written as `USING (TRUE)` grants access to everyone. Every policy in the inventory has been written to permit only a specified actor class under specified conditions. The default for any unmatched case is denial by absence of a matching permissive policy.

## Consequences

### Required maintenance discipline

The enforcement architecture creates obligations:

1. Any new governed table must have RLS enabled and at minimum a DELETE-denied policy before any data is inserted.
2. Any new trigger must be audited against the trigger inventory in VOCABULARY_RLS_MATRIX.md §3 to confirm it does not duplicate, contradict, or weaken an existing trigger.
3. Any new helper function with SECURITY DEFINER must be reviewed against SECURITY_DEFINER_REVIEW.md to confirm: search_path is set, ownership is correct, recursion risk has been assessed, and privilege is minimum-necessary.
4. Any new RLS policy that calls a helper function must be verified to not create a recursive call chain.
5. Any change to the governance model that affects a database invariant requires a new ADR and a new migration. It may not be made by modifying existing trigger or RLS code in place.

### What this architecture does not protect against

The database-layer enforcement protects against unauthorized reads, unauthorized writes, unauthorized deletes, and structural invariant violations. It does not protect against:

- A compromised superuser role with RLS bypass (`SET session_replication_role = 'replica'`)
- Schema migrations that DROP and recreate tables, bypassing RLS
- Application logic that assembles a context manifest from data not obtained through the governed SELECT path
- Cultural authority determinations made incorrectly by human stewards

These risks are governed at the deployment, access control, and process level — not at the schema level.

### What this architecture explicitly does not do

- It does not encode business workflow steps in triggers.
- It does not evaluate DisplayPolicy display-context decisions inline in RLS.
- It does not orchestrate the supersession workflow.
- It does not enforce the cultural authority appointment process.
- It does not validate that the right humans approved an ApprovalRecord.

These responsibilities are assigned to the application layer and to human governance processes. The database trusts that the application has performed the correct governance steps; the database then enforces that the result of those steps is structurally valid.

## Architectural Invariants Preserved

This ADR records the nine invariants established in GOVERNANCE_ENFORCEMENT_MODEL.md v0.2 §17 as the permanent architectural baseline for all future enforcement decisions:

1. Governance records become permanent upon activation
2. Historical assertions are superseded rather than overwritten
3. Generated Events retain provenance
4. Governed actions require accountable authority
5. DisplayPolicy evaluation is fail-closed
6. AI cannot bypass governance
7. Cultural governance overrides AI where applicable
8. Approvals remain historically traceable
9. Permanent records preserve immutable provenance

Any proposed schema change, new trigger, modified RLS policy, or new helper function that would violate any of these nine invariants requires a new ADR documenting the exception, a Discovery Partner decision, and an update to this document.
